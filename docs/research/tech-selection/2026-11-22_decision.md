# 小蜗桌宠技术选型调研与最终决策

日期：2026-11-22。对应 [产品规格](../../../SPEC.md) 与 [技术架构](../../TECHNICAL_DESIGN.md)。

## 1 最终选择

第一版采用 **Electron + TypeScript + React + electron-vite + electron-builder + 官方 Live2D Cubism SDK for Web**。保持已审阅的主进程计时、纯逻辑渡夜引擎、独立桌宠与控制窗口架构。局部夜雨使用 Canvas 2D，音频使用 Web Audio，本地数据使用版本化 JSON。

这是一项基于需求匹配和实际产品源码的工程决策，不是框架性能排名。Electron 的主要收益是统一 Web 渲染环境、现成的系统事件接口，以及可参考的双平台 Live2D 产品实现。明确承担其自带 Chromium/Node.js 的体积和常驻开销；本次未在真实小蜗模型和目标电脑上测量内存、功耗，不声称它最轻。

| 层次 | 确定方案 | 具体约束 |
| --- | --- | --- |
| 桌面宿主 | Electron | 主进程独占会话状态、有效计时和系统控制 |
| 语言与界面 | TypeScript + React + CSS | React处理面板，不逐帧驱动模型 |
| 构建 | electron-vite | 主进程、preload、renderer分别编译 |
| 安装包 | electron-builder | Windows安装程序；macOS DMG，签名公证走平台流程 |
| Live2D | 官方 Cubism Web Framework + 匹配 Core | 通过Live2DAdapter接入，按真实模型锁定兼容版本 |
| 氛围层 | Canvas 2D + CSS | 独立于模型WebGL canvas，不引入Pixi或完整游戏引擎 |
| 声音 | Web Audio | 单一音频导演，隐藏窗口行为需验证 |
| 数据与测试 | JSON、Vitest、桌面集成验证 | 不引入服务端、SQLite或通用插件系统 |

electron-vite 明确提供三类入口的统一配置；electron-builder 的稳定文档覆盖双平台安装与签名。这是工具能力选择，不表示相对 Forge 已测得速度优势。[构建来源](sources/root_05_electron_vite.md)、[发行来源](sources/root_07_builder_stable.md)

框架与库的路线已经确定；具体 patch 版本在首轮模型和平台验证通过后写入锁文件。不要把“最终选型”误解成现在就随意填写未验证的版本号。当前 electron-builder 主页指向未发布的 v27 文档，稳定入口是 v26，实施时须核对稳定频道。[版本来源](sources/root_04_builder.md)

## 2 类似产品实际怎样实现

调查核对了仓库依赖、渲染源码、构建脚本、作者文档与发行说明。下表区分“源码有实现”“作者有发行”“本次实机通过”；本次没有安装运行这些产品。主要源码资料已固定提交链接。

| 产品或项目 | 查到的真实路线 | 平台与证据边界 | 可借鉴的内容 |
| --- | --- | --- | --- |
| Open-LLM-VTuber Web | Electron + React + TS + electron-vite + electron-builder；当前源码直接使用官方Cubism Framework | 有桌宠模式、Windows/macOS构建入口；本次未做双端图形验收 | 与本方案最接近；模型组件、hooks和宿主分离；有从Pixi封装迁到官方SDK的实际经历 |
| AIRI | Electron + Vue + electron-vite + electron-builder；Live2D独立包使用Pixi封装 | README有Windows和macOS发行入口 | 桌面宿主、角色渲染和控制界面分层；AI依赖不需要照搬 |
| TonyNa Desktop Pet | Electron + 普通JS + electron-builder；可选Live2D | 作者只确认macOS Live2D实测，Windows等是应用和打包检查 | 小型桌宠无需大型依赖树；打包通过不等于模型实测通过 |
| Kagami desktop vpet | Tauri 2 + Vue3 + Pixi8 + easy-live2d | Windows定向代码，存在windows crate依赖 | 独立设置窗不重复加载模型、分状态帧率、隐藏停更；包装库有本地修补 |
| DesktopMascot | Tauri 2 + Vue3 + Pixi6 + pixi-live2d-display；Rust管理窗口与托盘 | 有真实Live2D加载代码及双平台CI；访问时无公开Release | 证明Tauri双平台路线可实现，不等于成熟发行或完整满足本项目错误反馈 |
| Kurisu Live2D Runtime | Qt + Cubism Native + OpenGL；macOS系统窗口适配 | 当前构建定向macOS | 原生图形路线可行，但双平台移植和原生构建仍要承担 |
| VPet Simulator | C# WPF/WindowsForms，独立Core与PNG动画组件 | Windows项目；Live2D列为可扩展显示方案 | 值得借鉴计时业务与动画接口分离；不能照搬WPF满足macOS |
| VTube Studio | 官方公告可确认Unity SDK路线 | 这是VTuber工具，不是本需求同构的轻量计时桌宠 | Unity适合角色表达，但仍依赖SDK兼容和桌面窗口适配 |
| Live2DViewerEX | 官方确认桌面、壁纸和窗口模式，更新说明披露自定义SDK渲染移植 | 提供双平台产品；未核实其底层框架，不猜测 | 成熟产品也需要针对模型新旧版本兼容，而非“更新SDK就全部兼容” |

产品原始证据：[Open-LLM依赖](sources/live2d_15_openllm_manifest.md)、[当前模型代码](sources/live2d_16_openllm_adapter.md)、[AIRI](sources/products_airi_desktop.md)、[AIRI发行入口](sources/products_airi_readme.md)、[TonyNa](sources/products_tonyna_live2d.md)、[Kagami](sources/products_kagami_readme.md)、[DesktopMascot渲染](sources/products_mascot_runtime.md)、[CI](sources/products_mascot_ci.md)、[Qt实现](sources/products_kurisu_cmake.md)、[VPet](sources/products_vpet_csproj.md)、[VTube Studio](sources/live2d_09_vts_unity.md)、[ViewerEX](sources/live2d_10_viewer_product.md)。

两个排除的误读：

- **Live2Pet 不能当成常驻实时Live2D桌宠证据。** 它主要把模型动作导出为WebP/APNG或图集，Electron是预览与导出工具的宿主。[来源](sources/products_live2pet_readme.md)
- **不能说AIRI已经整体从Electron迁到Godot。** Kirie路线并行存在，文档明确Electron仍受支持；新路线还有模型、Windows行为与打包验证工作。[来源](sources/products_airi_kirie.md)

## 3 为什么最终仍选 Electron

决定因素不是项目数量，而是以下三条需求同时成立：实时Live2D、Windows/macOS、一套完整桌面行为——穿透找回、独立设置、睡眠锁屏、不中断计时及发行。

Electron提供两端锁屏和睡眠事件、忽略鼠标并转发移动事件等直接接口；AIRI提供双端发行参照，Open-LLM提供官方SDK桌宠的源码参照。这三类证据共同降低首版需要自行探索的适配面。[系统接口](sources/platforms_02_electron_power.md)、[鼠标接口](sources/platforms_14_electron_mouse_forward.md)、[AIRI发行](sources/products_airi_readme.md)、[Open-LLM画布](sources/live2d_17_openllm_canvas.md)

统一Chromium减少两端WebGL、音频和可见性行为的引擎变量，但不消除操作系统差异。Electron官方曾有macOS透明覆盖层触发下层窗口节流的回归，相关修复已合入主线；选定发行版本时仍须确认包含修复并复测。[运行时组成](sources/platforms_03_electron_runtime.md)、[问题](sources/root_02_overlay_issue.md)、[修复](sources/root_06_overlay_fix.md)

最终判断：在尚未提出明确安装包／内存硬上限、首版要求两端完整体验的条件下，优先降低平台集成风险。这个判断可被后续真实模型性能结果推翻，不包装成行业普遍结论。

## 4 为什么不选其他路线

| 路线 | 最强优势 | 本项目暂不采用的原因 |
| --- | --- | --- |
| Tauri 2 | 不随应用携带完整浏览器，且已有真实Live2D桌宠实现 | macOS WKWebView与Windows WebView2需双引擎验证；锁屏适配和部分后台行为要另补；不把代码原型等同完整产品 |
| Qt + Cubism Native／live2d-py | 原生窗口与图形控制，可绕过Web渲染层 | 需承担Native SDK图形链、C++或Python绑定、系统通知和双平台打包；现有样本不足以证明本项目总体更省成本 |
| Unity + Cubism SDK | 角色动作、演出和成熟工具链 | 本项目主要是系统窗口和设置；常见透明窗口插件不支持多窗口，需额外集成以维持已认可架构 |
| Godot + GDCubism | 原生游戏场景能力，已有双平台Live2D扩展 | 依赖非官方GDExtension及Native SDK版本组合；为简单夜雨与计时引入额外引擎层收益有限 |
| WPF／单平台原生 | 能精细控制单一系统，VPet有成熟先例 | WPF不覆盖macOS；分别开发AppKit和Windows客户端增加两套维护面 |

Tauri证据：[两端WebView](sources/platforms_07_tauri_webview.md)、[窗口和后台接口](sources/platforms_06_tauri_window.md)、[电源插件](sources/platforms_09_tauri_power_plugin.md)、[DesktopMascot](sources/products_mascot_manifest.md)。Qt证据：[透明窗口](sources/platforms_10_qt_transparent.md)、[系统事件](sources/platforms_12_qt_native.md)、[Python绑定](sources/live2d_12_live2d_py.md)。游戏引擎证据：[UniWindowController](sources/live2d_07_uniwindow.md)、[GDCubism](sources/live2d_08_godot.md)。

需要保留的准确边界：

- Tauri当前版本的macOS透明窗口已不再要求显式macos-private-api开关；不能再以过时限制淘汰它。这也不自动证明内部完全没有私有调用或一定能进商店。[发布说明](sources/platforms_04_tauri_transparency.md)、[源码](sources/platforms_05_tauri_source.md)
- Tauri安装后可以离线使用。只有在机器缺少WebView2且要求离线安装时，才需要计入离线运行时成本；本产品当前要求离线运行，不能故意附加更严格条件抬高Tauri体积。[分发说明](sources/platforms_15_tauri_distribution.md)
- “UniWindowController不支持多窗口”是该插件限制，不是Unity绝对不能多窗口。[插件说明](sources/live2d_07_uniwindow.md)
- 没有同一模型、同一设备与相同帧率的可靠对照，本次无法给Electron、Tauri、Qt作内存和功耗排名。小安装包与低运行占用是不同指标。[测量原则](sources/root_01_performance.md)

## 5 Live2D 为什么直接接官方 SDK

Open-LLM-VTuber的官方1.2发布说明记录了从pixi-live2d-display-lipsync迁到官方Web SDK，当前固定提交的lappmodel直接导入CubismUserModel，迁移已反映在源码中。Cubism官方Framework目前明确兼容5.3；这些证据支持以官方适配层作为本项目基线。[迁移](sources/live2d_04_openllm_migration.md)、[源码](sources/live2d_16_openllm_adapter.md)、[官方Framework](sources/live2d_01_official_web.md)

原版pixi-live2d-display的README、开发分支和稳定版本存在不同兼容范围，不能只读“支持所有版本”就选定。Kagami的easy-live2d有本地清理和时钟补丁；TonyNa也披露不支持新混合模式。这说明封装层便捷与版本维护成本要一起考虑。[原库](sources/live2d_02_pixi_original.md)、[manifest](sources/live2d_03_pixi_manifest.md)、[Kagami](sources/products_kagami_readme.md)、[TonyNa](sources/products_tonyna_live2d.md)

这并不表示Pixi路线不可用：untitled-pixi-live2d-engine已声明支持Pixi8及Cubism2–5。但本项目只有一只固定角色，不需要整套Pixi场景图和滤镜系统，暂不增加这一层依赖。[现代分支](sources/live2d_06_pixi_modern.md)

具体实现约束：

- Live2D单独使用WebGL canvas，夜雨单独使用Canvas2D；两个画布不共享上下文。
- React只挂载组件与接收状态，模型每帧更新由适配器负责。
- 模型命中与状态条命中联合判定，夜雨层不拦截鼠标；DPR和窗口缩放统一换算。
- 官方SDK的便利层需要自行封装：资源加载、动作映射、清理、hit test及异常恢复。这是明确的额外工作，不宣称比任何包装库接入更快。
- 模型若只有旧Cubism2资源，先评估重新导出或替换资源；不为未确定的旧格式预先引入第二套运行时。

Framework、Core、模型贴图和动作有不同的使用条件。官方Core不在Framework仓库内，需按官方SDK包和发行范围准备；第一版只支持固定小蜗，不扩大为任意模型导入工具。实际小蜗模型尚未提供，因此模型可分发性和SDK兼容不能视为已解决。[Framework许可](sources/live2d_14_sdk_license.md)、[SDK发行说明](sources/live2d_13_sdk_release.md)

## 6 调研直接改变的工程安排

1. 将“Electron临时候选”改为第一版确定路线；Tauri只在明确触发条件下重新评估。
2. 将“Vite与Forge候选”明确为electron-vite与electron-builder，参考Open-LLM及AIRI的实际工程入口。
3. 透明桌宠窗设置resizable:false，通过受控程序边界调整处理尺寸，必要时重建；不依赖操作系统拖边框缩放。[透明窗限制](sources/platforms_01_electron_window.md)
4. 局部穿透明确由命中测试加setIgnoreMouseEvents实现；不能依赖透明像素天然穿透。Windows高权限窗口影响鼠标转发时保留托盘恢复，不要求桌宠以管理员运行。[接口限制](sources/platforms_14_electron_mouse_forward.md)
5. 保留硬件加速，不用关闭GPU“修复透明”的旧技巧；将实际模型的WebGL和透明行为一起验证。
6. 不为隐藏音频直接全局关闭backgroundThrottling。先验证指定窗口的音频与状态通道，视觉停更由适配器主动控制。[节流说明](sources/root_03_background.md)
7. 不引入AI对话、语音识别、Python服务、模型市场或游戏引擎；同类产品有这些功能不代表小蜗需要。

## 7 反证审查与假设结果

| 审查问题 | 证据与结论 |
| --- | --- |
| 是否只是为原先Electron猜测找支持？ | 搜到并核查了真实Tauri双平台原型、Windows Tauri产品、Qt Native和Unity插件；都承认可行。选择依据是本项目需求组合，不是“别的做不了” |
| 是否把成熟或知名等同适合？ | VPet虽成熟但WPF不符合macOS；Live2Pet虽有双端安装包却是导出器，均排除直接照搬 |
| 是否把README、CI当实机结果？ | 每个样本分开写源码、发行、作者测试范围；TonyNa和DesktopMascot明确保留图形实测缺口 |
| 什么证据会推翻结论？ | 实际小蜗在Electron长期运行超出已确定资源预算，且等负载Tauri或Native方案同时通过窗口和计时验收；或目标变成严格小体积、单平台原生产品 |

H1获得需求匹配层面的支持，未得到开发工时基准证明；H2确认“不能从安装包推导运行性能”，具体性能大小未定；H3获得官方SDK、实际迁移、其他产品兼容约束三方支持；H4由VPet、DesktopMascot和TonyNa的不同覆盖范围支持。

综合结论使用多家独立产品作者、框架维护者和SDK提供方，以及代码、官方文档、发行与问题记录交叉核验。技术资料以一手证据为主，没有用重复新闻凑来源数。没有三家独立同负载实验的性能论断标为证据不足；具体API事实只由对应官方资料支持，不冒充三方验证。

## 8 后续验证关口

技术路线在此确定。以下是实现验收的前置验证，不是继续无期限比较框架：

| 关口 | 要证明什么 | 失败后的动作 |
| --- | --- | --- |
| 真实小蜗模型 | 加载、动作映射、透明背景、表情与正确资源释放 | 优先修正模型或SDK适配，不先换整个宿主 |
| 双平台桌面 | 非聚焦、穿透恢复、缩放、拖动、屏幕拔插、管理员前台窗口 | 修正PlatformAdapter；存在无法绕过的核心缺口才复议宿主 |
| 完整渡夜 | 40分钟精度，锁屏、睡眠、隐藏和崩溃恢复 | 修复主进程时钟、保存与系统事件，禁止拿动画计时兜底 |
| 常驻成本 | 同一模型、同尺寸、30FPS、同粒子量，测整个进程树的内存、CPU、GPU、功耗；区分待机／战斗／隐藏 | 先降无效渲染、按需窗口与DPR；仍超预算则做同负载Tauri对照 |
| 发行 | 真正可安装的Windows与macOS包、资源离线可用、SDK与模型分发条件落实 | 修复打包或素材范围，不把开发环境跑通当成发行成功 |

比较必须记录硬件、系统版本、模型大小、运行时版本、完整进程树与测量口径。不能只测Electron主进程或只报Tauri主可执行文件大小。资源预算在真实模型首次验证时明确写入验收记录；本次不编造一个没有目标设备依据的毫秒或MB结论。
