# 小蜗桌宠技术选型调研计划

日期：2026-11-22。类型：深度技术决策。当前已有 SPEC.md 与待审阅架构文档，没有既有选型研究。用户认可模块架构，要求通过类似产品调研确定最终技术栈。

## 决策和假设

决策范围：Windows 与 macOS 的独立 Live2D 桌宠，支持真实缩圈时间线、设置、轻互动、睡眠恢复与离线运行。架构分层保持，桌面宿主和模型渲染实现可替换。

- H1：Electron 的桌面 API 和一致渲染环境，可以减少第一版跨平台接入工作；若相似 Tauri 产品已提供成熟完整实现，则削弱此判断。
- H2：Tauri 的小安装包不等于同等模型和双平台下更低运行成本；需要同负载实测才能确定资源收益。
- H3：模型渲染与宿主应分离；官方 SDK 可以避免受第三方封装版本上限约束，但可能增加接入成本。
- H4：现成桌宠项目通常只覆盖本项目需求的一部分，不能按星数或相似截图直接复用全部架构。

## 分工和来源

产品线检查真实仓库及构建文件；平台线检查 Electron、Tauri、Qt 文档及问题记录；Live2D 线检查 SDK、包装库和 Unity 等实际产品；主线负责反证、三方交叉核验、决策报告与架构修订。

可用渠道为联网搜索、官方网页、公开仓库文件与本地文档。无需外部账号或 API 密钥，不读取无关环境凭据。技术结论只引用官方文档、原始代码、维护者问题记录和产品官方资料。

每个使用来源独立记录 URL、访问日期、短原文摘录、可信度／时效／偏差及适用边界。综合决策尽量覆盖至少三家独立主体以及代码、文档、产品说明／问题记录等证据类型。单一 API 事实按官方文档标明；无法满足三源的广泛结论标为证据不足，不以转述网页补数量。

## 反证与风险

- 主动检索 Tauri Live2D 桌宠和 Electron 透明窗、隐藏窗口音频、睡眠事件问题。
- 不把主流、下载量或单个平台成功当成双平台适合。
- 不把闭源产品技术栈猜测当成事实；不把仓库列出的目标平台当成实机测试通过。
- 不把安装包小当成运行内存低；不引用不同负载的性能数字作直接排名。
- 区分模型素材许可、Cubism Core 条件和应用源码许可。

## 停止条件与交付

覆盖至少四种技术路线、六个有代表性的相似产品／项目；找出最强替代方案，明确为什么采用或不采用；锁定核心选择与可变边界；为不能远程核实的桌面行为指定验证项。完成来源索引、原子发现、决策报告、更新目标和架构修订。不启动产品实现、不安装 SDK、不提交 Git。
